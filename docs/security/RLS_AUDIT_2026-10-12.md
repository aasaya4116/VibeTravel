# Row-level security audit — October 12, 2026

## Scope

The audit covers every application table created by `scripts/001` through
`scripts/012`: profiles, trips, family vibes, saved attractions, Scout history,
the three feedback tables, trip shares, and trip readiness.

## Findings resolved by migration 013

- Legacy policies were not explicitly limited to the `authenticated` role.
- Several update policies did not state an explicit `WITH CHECK` condition.
- Saved attractions, chat messages, feedback, shares, and readiness records
  could carry a `trip_id` owned by a different user if a caller supplied a
  mismatched owner field.
- The three feedback tables and chat history used broad `FOR ALL` policies even
  though current product workflows only require append access (plus read access
  for Scout history).
- A user could delete the profile row directly without deleting the Supabase
  Auth account, leaving the account in a partially deleted state.

## Resulting access model

| Table | Authenticated-user access |
| --- | --- |
| profiles | Read, create, and update own row; no direct delete |
| trips | Read, create, update, and delete own rows |
| family_vibes | Read, create, update, and delete own row |
| saved_attractions | Manage own rows, only for an owned trip or no trip |
| chat_messages | Read and append own history, only for an owned trip or no trip |
| feedback_pulses | Append own feedback, only for an owned trip or no trip |
| feedback_outcomes | Append own feedback, only for an owned trip or no trip |
| feedback_messages | Append own feedback conversation rows |
| trip_shares | Manage own links for owned trips |
| trip_readiness | Manage own readiness record for an owned trip |

Trip ownership is checked twice: by RLS for API requests and by triggers for
privileged/direct database writes. Trip ownership itself is immutable. The
public shared-trip reader remains the narrowly scoped `get_shared_trip` RPC;
there is still no anonymous table-read policy.

All four reviewed `SECURITY DEFINER` functions pin the exact trusted
`pg_catalog, public, pg_temp` search path. Trigger functions have no API execute
grant; `get_shared_trip(text)` is the sole intentional definer RPC available to
`anon` and `authenticated`, and the verifier confirms it remains a definer.
`PUBLIC`, `anon`, and `authenticated` cannot create objects in `public`, so an
API caller cannot place an untrusted object in a definer function's path. Any
additional definer function fails verification until it is reviewed explicitly.

Migration 013 recreates all four definer functions from reviewed source before
assigning the trusted `postgres` owner or granting any RPC access. Verification
compares their stored bodies and core function properties, not only their
names. It also verifies that `handle_new_user()` is attached as the sole exact
enabled `AFTER INSERT` row trigger on `auth.users`. Ownership triggers are
checked by table, function, timing, event, absence of trigger arguments or
`WHEN` clauses, transition/constraint properties, and the exact `UPDATE OF`
column list derived from PostgreSQL's `tgattr` catalog field.

Scout and feedback server routes continue to work because both user and
assistant messages may be appended with the authenticated user's Supabase
client. The row's `user_id` must still match `auth.uid()`.

## Apply and verify

1. Confirm the Supabase project URL is the VibeTravel production project.
2. Run `scripts/013_harden_rls_policies.sql` in the Supabase SQL editor.
3. If preflight reports a cross-owner row, stop and inspect it; the migration
   deliberately does not delete or reassign user data.
4. Run `scripts/verify_rls.sql`. It must print `RLS verification passed` and
   return the final policy inventory.

The verifier also scans every ordinary or partitioned table currently in the
`public` schema, not only the ten tables known today. The 28 approved policies
are compared by table, command, role, permissive mode, and complete canonical
`USING` / `WITH CHECK` predicates. To preserve security-significant grouping,
the verifier asks PostgreSQL itself to parse and deparse the reviewed predicates
on session-local temporary mirror tables, then compares that output exactly; it
does not remove parentheses with regular expressions. Those temporary objects
are dropped automatically at transaction commit and no application data is
written. A policy on a future table fails closed until it is added to that
reviewed manifest; merely enabling RLS is not treated as a review of an access
policy.

Schema grants are read from the namespace ACL directly. PostgreSQL's `PUBLIC`
pseudo-role is checked as ACL grantee OID `0`; effective `anon` and
`authenticated` access is checked separately. This avoids treating `public` as
a catalog role while still catching direct and inherited schema-create access.

Supabase Storage is inventoried separately. No Storage policy is required while
the project has no bucket, but any latent Storage policy is audited even when
the bucket count is zero. If a bucket is introduced, it must be private, RLS
must remain enabled on `storage.buckets` and `storage.objects`, and object
policies must be authenticated-only and explicitly scoped by both `auth.uid()`
and `bucket_id`. Public buckets, anonymous policies, `FOR ALL` policies, and
unqualified `true` access fail verification.

## Production execution

Migration 013 was applied on October 12, 2026 to the VibeTravel production
Supabase project (`ttgncfexhoeupbzwwtbw`). Its preflight completed without any
cross-owner relationship violations. The complete `verify_rls.sql` audit then
ran successfully against the live schema without an assertion or catalog
mismatch.

The migration and verifier remain committed as reproducible source; future
schema or policy changes should rerun the same verifier before release.
